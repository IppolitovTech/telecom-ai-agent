# Архитектура

## Общая схема

Вместо непрозрачного `AgentExecutor` с ReAct-циклом — явный workflow с отдельными ветками обработки запроса.

```
                  ┌──────────────┐
                  │ User message │
                  └──────┬───────┘
                         ▼
                  ┌──────────────┐
                  │ Router/Agent │  ← решает: нужен поиск, tool или прямой ответ
                  └──────┬───────┘
                         │
             ┌───────────┼────────────┐
             ▼           ▼            ▼
        RAG search   Tool call   Direct answer
             │           │
             └─────┬─────┘
                   ▼
             ┌────────────┐
             │ Final LLM  │  ← собирает найденный контекст/результат tool в ответ
             └─────┬──────┘
                   ▼
        structured response { reply, tool_calls, sources }
```

Router — явный LLM-вызов с classification-промптом (`rag_search` / `tool_call` / `direct_answer` / `combined`). Для веток `rag_search`, `tool_call`, `direct_answer` — прямой вызов без циклов. Для ветки `combined`, где заранее неизвестна глубина рассуждения (нужен и поиск, и tool, и, возможно, уточнение), используется ручной ReAct-цикл (обычный `while` в Python, без `AgentExecutor`) с жёстким лимитом итераций.

## Сценарии

**RAG-сценарий:**
> «Как подключить роутер MikroTik после установки?» → `search_docs` → ответ с указанием источника.

**Tool-сценарий:**
> «Проверь статус моей заявки 12345» → `check_order_status(12345)` → «Your installation request is currently scheduled...»

**Комбинированный сценарий:**
> «У меня пропал интернет. Что проверить и какой статус моей заявки 12345?» → одновременно `search_docs(...)` и `check_order_status(12345)` → один финальный ответ, синтезирующий оба результата.

## RAG-слой

```
Document → Chunking → Embedding model → Vector store → Similarity retrieval
```

Chroma — это только vector store, слой хранения и поиска по векторам. Качество поиска определяется моделью эмбеддингов, а не самим Chroma. Для русскоязычных документов используется `intfloat/multilingual-e5-small` (HuggingFace).

## Глоссарий терминов

| Термин | Что это простыми словами |
|---|---|
| **RAG** | Вместо ответа «из головы» — сначала находим релевантные куски в своих документах и передаём их модели как контекст |
| **Чанкинг / overlap** | Документ режется на куски по 500–800 токенов; overlap — повтор небольшого фрагмента на границе соседних чанков, чтобы не терять смысл на разрезе |
| **Embedding model** | Модель, переводящая текст в числовой вектор, по которому ищутся «похожие по смыслу» куски. Именно она определяет качество поиска — vector store (Chroma) лишь хранит и ищет по этим векторам |
| **Vector store (Chroma)** | Хранилище векторов, оптимизированное под быстрый similarity search |
| **Router / intent classification** | Явный шаг, на котором LLM (или простой классификатор) определяет, что делать с сообщением: искать в документах, вызвать инструмент или ответить напрямую |
| **Tool / function calling** | Функция, которую модель может «вызвать» вместо текстового ответа — например, проверить заказ или создать тикет |
| **sources / citations** | Метаданные (документ, номер чанка, score), показывающие, на основе чего сформирован ответ — делают RAG видимым, а не скрытым внутри |
| **Retrieval accuracy** | Метрика: доля вопросов, для которых поиск вернул ожидаемый документ-источник — способ количественно проверить, что RAG действительно работает |
| **session_id / память** | Идентификатор диалога, по которому хранится история сообщений. В pet-проекте — просто словарь в памяти процесса, обнуляется при перезапуске сервера — осознанный, объяснимый компромисс, а не недосмотр |
